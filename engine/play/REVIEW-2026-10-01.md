# PS2 core review, October 1: ATV Offroad Fury 2

Play! branch `webstationx` through patch `play/0038`. Measured on the Ryzen 7 9800X3D + RTX 5090 desktop, headless
Chrome on the real GPU, asynchronous VPU1 thread, from `work/ps2-bench-states/atv2-race.st` (race start) unless noted.

| | before (core 30b2881fcbc9) | now |
|---|---|---|
| Game frames per second | 17–25 | 40–48 |
| Emulation speed (vblanks per second / 60) | 30–41%: slow motion | 100% |
| Terrain, minimap, gauges | red/black stripes, a font atlas for the minimap | correct |
| Resolution | same result at 1x, 2x and 3x | same |

(The ranges are the machine's own load on the day: back to back at the end, 25 fps at 41% before, 47–48 at 100%
after.) THPS4 (Foundry) and Dave Mirra 2 (Woodward) stay at 60 with 9–10 ms of limiter slack per frame; their single-thread
machine fingerprints are unchanged (THPS4 `89981dd97a117e3c`), so nothing here alters what those games compute.

## What was wrong

1. **The game computes on the GS and downloads the result.** Each frame it draws into an offscreen buffer
   (`0x8c000`, 384 wide): VIF codes as flat sprites (the alpha byte of a pixel is the command byte), noise textures
   blended with mip levels picked through Q and TEX1's K, and terrain heights as interpolated Z. It copies columns of
   that into Z buffer memory, downloads 2 × 3384 quadwords and sends them to VIF1 as the near terrain. The OpenGL
   renderer keeps alpha at twice its value, has no mip levels and stores depth as a float, so the packets came back
   wrong. `gs/GsSwRaster.h` now draws such targets in software straight into GS memory. It also removed ten
   `glReadPixels` round trips per frame.
2. **With the VPU1 thread on, DMA channel 1 finished too early** (a bug in our threading, not in Play!). The thread's
   queue takes a whole display list at once, so the channel's STR bit cleared at once. ATV2 took that to mean VIF1
   was through the list and moved on to the next frame's texture-upload list while the VIF interrupts of the list in
   flight were still coming: wrong textures and garbage downloads. One thread and synchronous mode were correct, which
   is how it was found: `?gstrace` and `?viftrace` from the same save state, diffed between synchronous and
   asynchronous runs. The channel now stays busy until the thread has taken its data. This may well be the stall
   the sampler-object experiment of September 30 ran into.
3. **Vector work took no emulated time.** The game waits for VIF1 before every flip; emulated, that wait was free, so
   it rendered 60 frames per emulated second, 135,000 triangles each, and the console ran at a third of its speed.
   With catch-up (play/0032) the EE cycles a frame is behind by are skipped once the frame is overdue: the game
   misses vblanks and drops frames, as on hardware, and sound and timers stay in real time.
4. **States captured in the middle of a frame lost register writes** (again our threading). Up to 255 GS register
   writes sit in a buffer before they are handed to the GS thread; they were neither saved nor dropped on load, so
   after loading a state they were drawn into the loaded frame. In ATV2 about one load in four put a stray VIF code
   into the terrain packets: VIF1 stalled on a MARK value the game's handler ignores, and the picture froze with the
   machine running. Found with the app's lifecycle test and `getPipelineState`; ten loads in a row pass since.
5. **Throughput.** VU1 computed MAC and sticky flags for every instruction although the microcode only reads clip
   flags (−25% VPU1 time). The EE ran its VIF status poll ~130 times per interrupt stall, 130 stalls a frame. The GS
   thread paid an atomic increment and a virtual call per register write and compared eleven registers per triangle.
   Sleeping threads took tens of microseconds to wake, 260 hand-overs a frame.

## Not established, and risks

- ATV2 is 40 fps in a race, not 60, on the fastest desktop CPU. The README's ATV2 section has the per-thread cost
  of a frame and the next steps (the GS thread split is the largest).
- Hardware accuracy of the software rasterizer is by the documented GS rules, not against a console: the result is
  a correct-looking terrain, and one-thread output is deterministic. Lines are not drawn on software targets.
- Catch-up changes timing whenever the host is behind: a game that can't drop frames will still slow down in
  game terms (its logic runs per frame) but keeps its sound. Settings → PS2 CPU speed → Full turns it off.
- A target becomes a software one when the game downloads it (never a displayed buffer; it reverts 600 flips after
  the last download). A game that downloads a large offscreen scene every frame would have it drawn in software.
- VU1 flag elimination assumes nothing outside VU1 microcode reads VU1's MAC/status flags (VU0 can map VU1's
  registers; no game doing that for flags is known).
- One "The core could not save its state" on suspending Harry Potter during its boot in seven app runs (the
  five-second limit of play/0030), before play/0038; not reproduced in ten saves in the bench or since.
- Save states made by cores before play/0038 with the thread on can already be missing register writes.
- Not tested on a phone or tablet. The spin count is lower there (`setVpu1SpinCount(4000)`).
- Not deployed to the Unraid server.

node engine/play/bench/probe.mjs --url http://localhost:8300/ --disc atv-offroad-fury-2/game.chd \
  --query "state=atv2-race.st&vu1thread=async&res=2" --secs 60 --vmprof 40:8
# speed = vblanks per second; game frames = gsStats.bufferFlips; catchup=0 in the query shows the old behaviour
